# ADR-0005: Encrypted case storage with Dexie

- Status: accepted
- Date: 2026-10-27
- Owners: Technical Director
- Task: TR-001 T4

## Context

Cases must stay illegible if someone with physical access copies IndexedDB. T3 already provides a
PIN-derived key hierarchy, a wrapped data key and AES-GCM record encryption with `table|id|version`
as AAD. T4 adds the persisted case model, a Dexie schema and a repository boundary. v1 has no backend,
no search and no separate tables for consent, screenings or referrals.

TR-001 §6.1 originally described `id` and `createdAt` as the indexed plaintext fields. T3 implemented
`actualizadoEn` and kept `createdAt` inside the ciphertext, so the specification text needed correcting
rather than adding a second plaintext timestamp.

## Decision

### Schema and plaintext metadata

- Keep the database name `saviatech`. Dexie version 1 keeps the `cryptoMetadata` table; version 2 adds
  `cases` with primary key `id` and index `actualizadoEn`. The upgrade only creates the new table, so
  the existing vault row is preserved.
- Store each case as a T3 `EncryptedRecord`: `{ id, v, iv, ct, actualizadoEn }`. No other field is
  persisted in clear.
- `id` is a random UUID generated by Web Crypto. It is the primary key and part of the AAD.
- `actualizadoEn` is monotonic ordering metadata. It is not authenticated and is not clinical
  evidence. `createdAt` lives inside the encrypted payload.
- One encrypted payload contains the pseudonymous code, the `synthetic` flag, `createdAt`, consent and
  all screenings. Consent, screenings and referrals are not separate tables. Referrals come from
  `content/` and are not stored.
- There is no blind index and no code search in v1.

### Repository

- `createCaseRepository({ db, keyring })` is a factory with injected dependencies and no global
  singleton. The UI imports through `storage/index.ts`; it never touches Dexie or a `CryptoKey`.
- Every operation uses `keyring.withDataKey`. A locked vault raises `VaultLockedError` and the
  repository neither catches nor translates it. `count` checks the keyring state for uniform behaviour.
- `create` generates the UUID, code and `createdAt`, validates with `parseCasePayload`, encrypts with a
  fresh IV and adds the row.
- `get` decrypts with the requested id, not `row.id`, validates the payload and returns `null` when the
  row does not exist.
- `list` orders by `actualizadoEn` descending and decrypts only the requested page. A row that fails
  authentication or validation with `CorruptDataError` is reported in `unreadableIds` without aborting
  the page. Other errors propagate. Page size defaults to 20 and is capped at 100.
- `update` follows an optimistic pattern: read and decrypt outside a transaction, apply the updater,
  validate, reject changes to `code`, `createdAt` or `consent`, encrypt with a new IV, then open a short
  read-write transaction that compares the original `actualizadoEn` and writes only if it still matches.
  A mismatch raises `ConcurrentModificationError`. No Web Crypto call runs inside the IndexedDB
  transaction, because the transaction can close while waiting for a non-IndexedDB promise.
- `updatedAt` is `max(Date.now(), previous + 1)` so it advances even if the clock does not.
- `changePin` continues to re-wrap only the data key. Case rows are not re-encrypted.

### Validation and persistence

- `parseCasePayload` validates shape, types, UTC `Z` timestamps, the code alphabet and the rule that a
  changed final band requires a non-empty justification. Shape errors raise `CorruptDataError`;
  invariant errors raise `InvalidCaseDataError`.
- `requestPersistentStorage` and `estimateStorage` wrap `navigator.storage` and report
  `granted`/`denied`/`unsupported` or `null`. They are not called at import time. T5/T6 decide when to
  request persistence and how to warn the professional.

## Consequences

- A raw IndexedDB dump reveals the database name `saviatech`, the table name `cases`, random ids, the
  format version, IVs, ciphertext sizes, the number of cases and their `actualizadoEn` values. It does
  not reveal codes, consent, answers, scores, bands, justifications or timestamps inside the payload.
- Case count and recency are visible. This can itself be sensitive in a hostile household; T8 must
  decide whether the database name becomes build configuration (D3).
- There is no anti-rollback protection: an attacker with write access can restore an older ciphertext
  for the same table, id and version. An authenticated counter or server-side sequence is future work.
- The optimistic check detects concurrent updates inside one database, but two tabs still hold
  independent keyrings and are not coordinated. Cross-tab locking remains an open limit.
- Page-only decryption keeps list cost proportional to the page, not the table. A low-end Android
  measurement is still pending.
- There is no search, backup, wipe, logical deletion or consent revocation in v1.

## Alternatives considered

- Store consent, screenings and referrals in separate tables: rejected because TR-001 keeps one case
  aggregate and separate rows would widen the plaintext surface and complicate atomic updates.
- Index `createdAt` in clear: rejected because T3 already persists `actualizadoEn`; adding a second
  timestamp would leak more metadata without a requirement.
- Add a blind index for the pseudonymous code: rejected for v1; there is no search requirement and it
  needs a separate design.
- Decrypt the whole table and paginate in memory: rejected because it scales badly and exposes more
  plaintext to one operation.
- Run encryption inside the IndexedDB transaction: rejected because Web Crypto promises can outlive the
  transaction and cause it to close.
- Re-encrypt every case on PIN change: rejected; re-wrapping the data key is sufficient and safer.
